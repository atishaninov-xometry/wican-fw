Context for continuing this fork (offline telemetry for a **2025 Mazda MX-5 ND3, manual**, via a **WiCAN Pro** OBD adapter). This file is the durable handoff: everything non-obvious lives here so work can continue in cloud/CI without the original local machine.

## Patches in this fork (all on both branches)
1. **1 s SD logging** — homepage logger slider min 10→1; `config_server.c` `log_period` parse/clamp [1,300]s.
2. **Manual RTC time (no NTP)** — `rtcm_set_from_unix()` (settimeofday + RX8130 BCD write); `POST /set_time`, `GET /get_time`; a **"Time" web tab** with: device time, "Borrow browser time" (stages phone clock), "Commit to RTC", and **"Sync from internet (NTP-like)"** (the phone's browser fetches UTC from timeapi.io/worldtimeapi.org and POSTs to /set_time — WiCAN stays offline).
3. **SD safe-eject button** (`main.c`, WICAN_PRO) — hold GPIO8 ~3 s while running → flush WAL + close SQLite + unmount FATFS; LED yellow=flushing, green=safe, red=error.
4. **Auto-flush SD on engine-off/sleep** (`sleep_mode.c`) — checkpoint+close+unmount in LOW_VOLTAGE→SLEEPING; wake does a full restart so the card remounts clean.
5. **Web-UI fix** — httpd `max_uri_handlers` 38→48 (the two new /set_time,/get_time handlers overflowed the limit and killed the wildcard static handler → whole UI broke).
6. **Periodic wakeup up to 24 h** — slider max 240→1440 min + `config_server_get_wakeup_interval` clamp →1440. Safe: `wc_timer` uses uint64 µs.
7. **Throughput, part 1** — inter-request gap 100 ms → **5 ms** (`AUTOPID_INTER_REQUEST_GAP_MS`, autopid.c). Part 2 (batching) is **DONE** — see below.
8. **"Debug" web tab (removed).** Ran on-car checks (connection, multi-PID batching, DSC header reset) via buttons instead of hand-typed Terminal commands — it did its job (see the batching capture below) and was removed once no longer needed. If similar checks are needed again, `git log` this file's history for `debug_tab`/`main/web/src/debug.js`.
9. **Fixed a real bug found while building the above**: `terminal.js`'s ELM327 mode sent commands as a raw CR-terminated WS text frame (`sendText`), but `ws_router_handle_frame` only dispatches terminal commands wrapped in JSON (`{"cmd":"..."}`) — a non-`{`-prefixed frame returns unhandled and falls into the raw `DEV_WIFI_WS` monitor queue instead of ever reaching `elm327_run_command`. **This is why manually typing `010C` in the Terminal tab produced no response at all** (not a missing-init issue, no partial output ever arrived). Fixed by sending `{cmd:...}` for both terminal types. Also bumped the terminal's per-command ELM327 response wait from 2000ms → 4000ms as a margin for a cold `ATZ`/first read (untested on hardware, low-risk since it only widens a manual-debug wait window).
10. **Multi-PID Mode-01 batching, implemented** (`components/autopid/autopid.c`, `autopid_poll_std_pids_batched()` + `autopid_isotp_reassemble()` + `autopid_std_pid_data_len()`) — see "RESOLVED: OBD poll throughput" below for the full story.

## ✅ RESOLVED: OBD poll throughput (multi-PID batching)
**Was:** standard PIDs logged at ~10 s regardless of the per-PID Period, because the poll loop sent one Mode-01 request per PID sequentially over the slow ND3 gateway — one full pass ≈10 s, so everything sampled at pass-rate.

**Confirmed on-car 2026-09-01** via the Debug tab's "Test multi-PID batching" (raw capture below) — the ND3 gateway happily answers a **6-PID batched Mode-01 request in one shot**:
```
> 010C0D0F11052F
7E8 10 0E 41 0C 0B 1C 0D 00
7E8 21 0F 55 11 1D 05 8A 2F
7E8 22 DF 00 00 00 00 00 00
```
Reassembled (First Frame + 2 Consecutive Frames, standard ISO-TP): `41 0C 0B1C 0D 00 0F 55 11 1D 05 8A 2F DF` → RPM 711, Speed 0, IntakeTemp 45°C, Throttle 11.4%, Coolant 98°C, Fuel 87.5% — every value physically sane, throttle position matched exactly across two separate polls seconds apart. **Wire format: ONE leading `0x41`, then concatenated `(PID, data...)` pairs in request order — not `41 PID data` repeated per PID.** That one fact broke the Debug tab's own first-pass verdict parser too (it assumed a repeated `41`, so it always undercounted — fixed in `debug.js`'s `decodeMultiPidBatch`/`isotpReassemble`, verified against this exact capture).

**Implemented in `autopid.c`:**
- `autopid_isotp_reassemble()` — classic (non-FD, 8-byte-frame) ISO-TP reassembly from the bytes `parse_elm327_response()` already concatenates into `response->data` (that function keeps PCI bytes in-band, one physical CAN frame = one 8-byte chunk — reused as-is rather than touching that parser).
- `autopid_std_pid_data_len()` — canonical data length per PID from the existing `obd2_standard_pids.h` table (independent of which of that PID's params happen to be enabled).
- `autopid_poll_std_pids_batched()` — called once per poll pass, **before** the existing per-PID loop. Collects up to 6 unique due `PID_STD` PIDs (de-duping when two enabled params share one PID, e.g. two bit-ranges of the same response), sends `01`+concat as one request, reassembles, walks PID-by-PID building a synthetic `[0x00][0x41][PID][data...]` buffer per PID and reusing the existing `extract_signal_value()` unchanged (lowest-risk reuse, exactly as planned). Any PID it services gets its timer re-armed immediately, so the old per-PID loop below just finds it not-due and skips it — **no restructuring of the existing loop**, `PID_CUSTOM`/`PID_SPECIFIC` are completely untouched. Fail-safe: on any PID-marker mismatch mid-batch, everything from that point on in the batch is marked failed rather than guessed; already-decoded earlier PIDs in the same batch stand.
- **Also fixes the DSC-header-stuck TODO as a side effect**: every batch unconditionally resends `standard_init` (protocol + `ATSH7DF`) right before sending, so a custom/specific PID leaving the header on 760 can no longer wedge standard PIDs for the rest of the drive. (The chip-level reset was independently confirmed clean in the same Debug-tab session — see the DSC finding below.)
- **Real-drive regression found and fixed (2026-09-01 evening, `batch_timing.csv` from an actual drive):** every batch of 2+ PIDs failed (`success=0`) at the SAME ~35-50ms round-trip as successful single-PID requests — not a gateway/timeout problem, something was rejecting good responses after the fact. Root cause: `autopid_validate_response_for_cmd()` (autopid.c, gated by `pid_validation_en`, **default enabled**) checks that the request's extra bytes appear *contiguously* right after the positive-response service byte (correct for a single multi-byte identifier like Mode 22 `22 B0 02` → `62 B0 02`) — but a batched Mode-01 request's PIDs are independent, so the real response is `41 PID1 data... PID2 data...` with data bytes *between* the PIDs, never contiguous. So every batch got overwritten with `"error"` before `autopid_poll_std_pids_batched()` ever saw it. This is exactly why the earlier Debug-tab confirmation looked clean: that path (`elm327_run_command`, the Terminal/WS-monitor code) never goes through `autopid_parser`/this validator at all — only the real `elm327_process_cmd`-based poll loop does, so the bug was invisible until an actual drive exercised it. **Fixed**: `autopid_validate_response_for_cmd()` now special-cases `service==0x01 && req_len>2` (a genuine multi-PID batch) to just confirm a `0x41` positive-response byte is present, deferring to `autopid_poll_std_pids_batched()`'s own per-PID resync-checked walk for real correctness — unchanged behavior for single-PID/Mode-22-identifier requests.
- **Round-trip latency, for the 10-20Hz-on-a-few-PIDs question:** confirmed with a post-fix drive (273/273 batched requests succeeded) at a flat **~34-37ms per request, independent of batch size** (1-5 PIDs) — far better than the ~770ms/PID estimated from the old pre-batching pass-time math. At that rate a small RPM/speed/gear batch is nowhere near latency-limited; 10-20Hz is plausible for a small PID subset. The one-off `batch_timing.csv` instrumentation used to measure this has since been removed from the firmware (its job was done) — see "SD logging facts" below.

## Key ND3 findings (validated)
- **ND3 = CX-60-gen electronics. OBD port exposes ONLY diagnostic req/resp (Mode 01/06/09/22) — NO raw broadcast frames.** Raw sniffing at OBD sees only poll responses. Many-signals-at-high-rate needs an internal bus tap (not the OBD port). Ref: https://github.com/drewid74/2024-nd3-mazda-obdii
- **Gear decode: gear is in the HIGH NIBBLE of byte B → `B4/16`.** GearStatus (PID 01A4): 0=Neutral, 1..6=gear. RecommendedGear (PID 0165): 0=none, 2..6=shift-up hint. The Standard-tab "A4 gear RATIO" is noisy on ND3 — use the enum.
- **Steering is DEAD at the OBD port.** DSC PIDs 22 2033/2034 respond but never vary; 201D constant, 201F NO DATA. Needs an internal tap.
- **DSC (header 760) PIDs BREAK the standard engine PIDs — but only because the firmware didn't reset the header, not a chip limitation.** Confirmed on-car 2026-09-01 (Debug tab "Test DSC header reset"): baseline `010C` → `ATSH760`+`222033` → `ATSH7DF` → follow-up `010C` all succeeded (RPM 714→711) — the raw ELM/CAN link resets cleanly at the chip level. The real bug was the poll loop only resending `standard_init`/`ATSH7DF` on a `pid_type` transition, which a 760 query didn't reliably trigger for every subsequent standard poll. **Fixed as a side effect of the batching poller** (`autopid_poll_std_pids_batched()` resends `standard_init` unconditionally before every batch) — worth re-adding brake pressure / re-testing DSC-alongside-standard on the next drive to confirm end-to-end, not just the manual chip-level probe.
- **Expression parser** (`main/expression_parser.c`): `+ - * /`, bitwise `& | ^`, shifts `<< >>`, parens. Operands: number, V, `Bn`(unsigned byte), `Sn`(SIGNED byte), `[Bn:Bm]`(unsigned multi-byte), `[Sn:Sm]`(SIGNED multi-byte), `Bn:bit`. **NO comparison (`< > ==`), NO functions.** For signed use `[Sn:Sm]` — NOT `(Bn>127)*65536` (fails eval).
- **AutoPID profile IMPORT format:** must be the **array/converted form** (`parameters:[{name,expression,unit,class,min,max,type,period,send_to}]`). The shorthand map form (`parameters:{Name:"expr"}`) makes the UI fetch `params.json` from GitHub with no timeout → **hangs forever offline**. (main.js:454 = array form skips the fetch.)
- Byte index: mode01 A=B3,B=B4,C=B5,D=B6; mode22 A=B4,B=B5.

## SD logging facts
- AutoPID SD logger = SQLite under `/sdcard/obd_logs`, decoded PIDs only, **delta-logging** (only changed values), `synchronous=OFF` during inserts (nothing durable until checkpoint/unmount — hence the safe-eject/sleep-flush patches). Rollover at **4 MB/file**, keep newest **100** files (count-based only, no free-space guard). Param IDs are **per-file** (each rotated .db recreates `param_info`) — map through each file's own `param_info` when merging. `db_index.json` = the file manifest.
- **Extract a log cleanly:** engine-off (auto-flush) or safe-eject (green LED) BEFORE downloading, else a live web-UI download of the active .db can be 0 bytes / missing WAL rows.
- **Batch round-trip timing (removed).** `autopid_log_batch_timing()` wrote `/sdcard/obd_logs/batch_timing.csv` (one row per batched Mode-01 request) for exactly one purpose: measuring the real per-request latency floor for the 10-20Hz-on-a-few-PIDs question. It did its job (confirmed ~35ms flat, see the "RESOLVED" section above) and was removed from `autopid.c` once no longer needed, to stop the extra SD writes. If similar timing capture is needed again, git log this file's history for `autopid_log_batch_timing`.
- **Logger interval slider bug (fixed).** The webUI's "Log Period" range input never got its `.value` synced on page load — only the adjacent text label was updated (`main.js`, `log_period_value`), so the slider itself silently stayed at its HTML default (10s) regardless of the actually-saved config. Submitting *any* settings change (not just this one) then resent that stale default and overwrote the real `log_period` back to 10, even though the UI displayed the correct saved value. This is why a device configured for 1s logging kept writing at a hard 10s cadence (`obd_logger.c`'s independent write timer falls back to `logger_period*1000`, and `logger_period` was legitimately being persisted as 10, not 0). Fixed by also setting `document.getElementById('log_period').value = obj.log_period;` on load.
- **Poll interval vs. SD write interval, split to reduce flash wear.** The single "Log Period" used to gate both sampling live values AND writing them to the SD card, so a short interval for fine-grained data meant frequent SD writes. Now two independent knobs: **Logger Sample Interval** (`log_poll_period` config key, **milliseconds**, default 10ms, range 10-300000) = minimum spacing between recorded samples *of one parameter*; **SD Write Interval** (`log_period`, seconds, default **5s**, floor 1s, ceiling 300s) = how often the RAM buffer is flushed to the card. See the millisecond-resolution bullet below for how samples actually get in.
- **Standard PID Period floor dropped 1000ms -> 10ms.** The Automate/Standard-PIDs tab rejected any Period below 1000ms on save (`main.js` client-side validation only — `main/config_server.c`/`autopid_config.c` never clamped it) even though batching (see RESOLVED section above) makes far faster per-PID polling achievable now. Lowered to 10ms alongside the Logger Sample Interval floor. Actual achievable rate for a given PID is still capped by real batch round-trip time (~35ms/batch of up to 6 PIDs) and how many PIDs are enabled — setting Period=10ms just means "poll this PID every pass, as fast as the batching loop can go," not literally 100Hz.
- **⚠️ Logger Sample Interval does NOT speed up OBD acquisition — confirmed by user test, initially mislabeled "Poll Interval".** Lowering it to 100ms did nothing to how fast PIDs actually update. Nothing in Logger Settings talks to the car: the OBD query rate for a given PID is controlled by *that PID's own* `Period` (ms) on the Standard PIDs / Vehicle-Specific tab. Deliberately did NOT make this field override per-PID Periods (it would silently clobber PIDs intentionally tuned slower, e.g. coolant temp at 10s). To make RPM/speed/gear refresh faster, lower those PIDs' own Period; batching is what makes a fast Period achievable at all.
- **Manual exact-value entry + natural-language duration parsing (webUI).** Logger Sample Interval, SD Write Interval, Sleep After, and Wakeup Every each pair their slider with a free-text box backed by a small vendored parser (`main/web/src/duration_parser.js`, embedded like the other JS files — no CDN, the device is often offline on its own AP) understanding things like `10ms`, `2h`, `10 hours`, `1h 30m`. Both controls write into one shared hidden input (id = the field's original name, e.g. `log_period`) which is what actually gets submitted — the visible `<input type=range>` was renamed to `<id>_slider` and the text box is `<id>_text`, so a typed value outside the slider's own min/max range isn't silently clamped by the range input. `durationSetAll`/`durationApplyMs`/`durationSliderInput`/`durationTextInput` in `main.js` are the shared glue for all four fields.

- **⏱ Millisecond-resolution logging (rework, commit `f31ae72`).** Sub-second logging was impossible no matter what the intervals said, for nine separate reasons - all fixed:
  1. `param_data.timestamp` held Unix **seconds** (`rtcm_get_unix_timestamp()`, which also does an I2C read of the RTC per call). It now holds **epoch milliseconds** from `gettimeofday()` (µs-resolution, no I2C; the system clock is set from the RTC at boot in `main.c`). **Analysis scripts must now use `timestamp/1000`.** `datetime(timestamp/1000,'unixepoch')` in `obd_logger_query_param`, the query's time-range bounds, and `obd_logger_get_latest_time` were all updated with it.
  2. One timestamp was bound **once per flush**, so every row in a batch shared it. Now bound per row.
  3. Only the newest value per param survived a flush - a fast sample rate was thrown away at write time. Samples now accumulate in a **PSRAM double buffer** (`SAMPLE_BUF_ENTRIES` 8192 × 16B × 2 = 256KB) and all of them are written.
  4. Sampling used to be a timer that re-read a **JSON snapshot** of all params (`autopid_data_read()` malloc + `cJSON_Parse` per tick). Samples are now **pushed from the acquisition path**: `obd_logger_record_sample()` called from `autopid_prepare_parameter_value()`, the single funnel every accepted value passes through (batched STD, per-PID STD, custom PIDs, CAN filters). A row is therefore stamped when the value *arrived*, not when a tick noticed it - no aliasing.
  5. `autopid_task` slept **100ms at the end of every poll pass**, capping every PID at ~10Hz regardless of its Period. Now `AUTOPID_POLL_PASS_YIELD_MS` = 2ms.
  6. Every re-armed poll timer got **±100ms random jitter**, making any period under ~200ms meaningless. `autopid_rearm_param_timer()` now caps jitter at period/4.
  7. **After a DB rotation, `param_info` was left empty and the RAM lookup kept the old per-file ids**, so every rotated file's rows resolved to no parameter. At a fast sample rate rotation happens every few minutes, so this was fatal. `obd_logger_repopulate_params()` (called from the rotation-completed event, with `db_mutex` already held) re-inserts the params and refreshes the ids; buffered samples carry a **lookup index**, resolved to a row id at write time under `db_mutex`, so a rotation mid-buffer can't mislabel them.
  8. `param_lookup` gained a retained `data[128]` metadata copy for that repopulation, plus `last_value`/`last_ts_ms` for the spacing + delta gates.
  9. The logger task is now only a **flush supervisor** (50ms tick): it flushes when the write interval elapses *or* when the buffer crosses `SAMPLE_BUF_HIGH_WATER` (75%), so a fast sample rate can't overrun a slow write interval. Overruns increment a dropped-sample counter and log a warning.
  - Locking: `sample_mutex` guards the buffers + the mutable `param_lookup` fields and is **never held while touching the DB**, so acquisition never blocks behind an SD write. Flush takes `sample_mutex` (swap) then releases it before taking `db_mutex` - no nesting, no cycle.
  - **Hard physical limit that remains:** the ND3 gateway answers in **~35ms per request** (1-6 PIDs batched, measured over 273 real requests), so *fresh* data caps at **~28Hz**, not 100Hz. Timestamps are now precise to the millisecond, but two rows 10ms apart can only differ if the gateway actually answered in between. Finer than ~35ms needs an internal bus tap, not firmware.
  - Volume: ~16 params at the ~28Hz ceiling ≈ 450 rows/s ≈ 11KB/s → 4MB per ~6min, so the 100-file cap is ~10h of continuous logging.

## Build / flash quick reference
- CI: push to `sd-logging-patches-*` or run **Actions → "Build firmware (WiCAN Pro, IDF 6)"**. Every successful build is now also published as a **GitHub Release** (`build-<run_number>-<branch>` tag, `softprops/action-gh-release`, `target_commitish` pinned to the actual built commit — don't omit that input, it defaults to `main` otherwise and the release silently stops showing up against the real commit) — `.../releases/latest` always resolves to the newest one; the 30-day-expiring Actions artifact (`wican-fw-obd-pro-*`) still exists too if you'd rather grab it from the run page. `actions/checkout`/`actions/upload-artifact` are pinned to `@v7` (bumped from `@v4`); `espressif/esp-idf-ci-action@v1` is already latest.
- OTA flash: web UI → **System → Firmware Update** → upload `wican-fw_obd_pro_*.bin` (rollback is DISABLED in this build, so keep a USB recovery path). USB full-flash offsets: 0x0 bootloader, 0x8000 partition-table, 0xd000 ota_data_initial, 0x10000 app (chip esp32s3, dio, 16 MB, 80 m).
- WiCAN Pro AP default UI: `http://192.168.0.10`, AP pass `@meatpi#`. Version = About tab.
